# 0G Private Computer

## What breaks if 0G is removed, in one sentence

**Without a verdict from somewhere neither side controls, nobody stakes
anything — because the only parties left to judge whether a report is fabricated
are the maintainer, who collects the slashed bond, and us, who wrote the rules.**

That is not a nice-to-have. The whole mechanism is a bond that can be kept, and a
bond that can be kept by the person deciding is not a bond, it is a fee. Delete
the 0G call and the product is a payment form with extra steps.

---

## Where the inference sits in the flow

```
reporter submits  ──►  enclave reads it  ──►  maintainer sees the opinion
                       (0G, TeeML, TDX)       and signs the outcome
                            │                        │
                            │                        ├─ Valid      → refund + tier
                            ▼                        ├─ Good faith → refund
                     request id + provider           └─ Fabricated → slash
                     stored next to the bond
```

The triage desk is the product. A maintainer opens it the way they open an
inbox — that is the reason to come back tomorrow, not the bond contract
underneath it. The enclave is what makes the desk safe to act on.

**The enclave never sentences anyone.** It returns a first opinion with three
possible calls, and a human signs the settlement. We never slash on an unreviewed
machine verdict, and the UI never presents the model's call as a decision.

### Three calls, because two would be unjust

| call | meaning | consequence |
|---|---|---|
| `valid` | real and reproducible | bond refunded, tier granted |
| `plausible` | good faith, unconfirmed | bond refunded **in full** |
| `fabricated` | cites code that cannot exist | bond slashed to the triage pool |

The middle one is load-bearing. Most honest security reports are wrong, and a
system that punishes being wrong drives out exactly the people it needs. The
system prompt says so explicitly: *"BEING WRONG IS NOT FABRICATION… If you are
unsure, the answer is plausible."*

## Which model, and how we know it is really in an enclave

0G's docs never say which models run **inside** the enclave. The catalogue does,
in a field that is easy to miss:

- `verifiability: "TeeML"` → the model runs in the enclave
- `verifiability: "TeeTLS"` → transport encryption only; it does not

Only **10 of 125** models carry a verifiability value at all (9 TeeML, 1 TeeTLS,
verified live 2026-11-06), and most are embedding, speech or image models. We pin
**`glm-5.3`**, and [`assertTeeML()`](../src/triage/zerog.mjs) refuses to run at
all if the catalogue stops reporting it as TeeML rather than quietly falling
back to something cheaper.

### What we verify

`GET /v1/providers?model=glm-5.3` returns three providers, and they are not alike:

| provider | trust mode | enclave |
|---|---|---|
| 0G Foundation `0xD179…E503` | `private` | **TeeML · TDX · dstack** |
| Baidu `0x0000…8044` | `standard` | none declared |
| Tencent `0x0000…8044` | `standard` | none declared |

Every completion returns `x_0g_trace.provider` — the address that actually served
it. `X-0G-Provider-Trust-Mode: private` keeps us on the first row, and
[`verifyProvider()`](../src/triage/zerog.mjs) checks the returned address against
the enclave list afterwards. **That is a check, not a self-report.** The request
id and the provider address are both shown on screen next to the verdict.

The header fails rather than downgrades: **503** when no enclave is free, **502**
when the enclave is down, never a silent reroute to Baidu. We treat both as
errors and say which one happened, because "the enclave was unavailable" and
"something else answered" must never look the same.

### What we cannot verify, stated plainly

**We do not fetch the provider's signature over the response.**
`GET {provider_url}/v1/proxy/signature/{chatID}` is real, but it belongs to the
direct-SDK flow where the caller holds the provider's URL. Through the Router it
is unreachable: no provider record carries a `url` field, and eight candidate
router-side paths all return 404 against a live chat id.

So the claim we make is the narrow one — *we verified which provider answered* —
and the UI says `signature: unavailable via Router` rather than implying a check
we never ran. If we could reach it, `resolve()` would ecrecover it on-chain; we
are not going to pretend we got there.

## Two things live probing caught

**1. A single-provider model is a single point of failure.** We originally pinned
`0gm-1.0-35b-a3b` — TeeML, TDX, 262k context, the cheapest TEE model on the
router. It has exactly **one** provider, and on 6 Nov that provider returned
`502 fetch provider quote: EOF` for hours. `glm-5.3` has two. Pick on provider
count, not on the spec sheet.

**2. A reasoning model can return nothing and look like it answered.** `glm-5.3`
thinks before it speaks: a real triage call spent **485 reasoning tokens** before
emitting any JSON. With `max_tokens: 900` the content field came back as an empty
string — not an error, not a short answer, *empty*. The original code would have
parsed that to `{}` and defaulted the call to `plausible`, which means **a
fabricated report would have been scored as honest and refunded**. Empty
completions now raise. Budget for the thinking, not just the answer.

## Cost and latency, measured

| | |
|---|---|
| cost per triage | **~$0.006** (187 prompt + 750 completion tokens) |
| latency | **17–30s**, most of it reasoning |
| trust mode | `private` |

Latency is honest rather than hidden: the desk shows a working state and the
request id lands when the enclave answers. For a maintainer clearing an inbox
this is the right trade; nobody needs a slop verdict in 200ms.

## Try it yourself

```bash
npm run zerog:models     # the live catalogue, with the verifiability column
npm run serve            # then open the Triage desk tab
```

```bash
# the raw call, with the trust header that does the work
curl -s https://router-api.0g.ai/v1/providers?model=glm-5.3 \
  -H "Authorization: Bearer $ZEROG_API_KEY" | jq '.data[] | {provider_name, trust_mode, tee_type}'
```

`/api/health` reports what the app actually reached, including both provider
lists, so you can see what the trust header is protecting the verdict from.
